# 多实体问题的证据覆盖优化

## 问题

用户问题“BeneVision N1 和 IntelliVue MX550 分别是什么设备？不要把配置混在一起。”同时包含两个明确型号。旧链路把整句作为一次检索请求，Top-K 被 MX550 和通用产品目录占满；生成答案可能包含两个型号名称，但引用中没有 N1 专属资料。

只检查答案关键词和引用数量会把这种结果判成通过。生产系统需要检查的是：每个显式实体是否都有可审计、已授权且适用的证据。

## 修复

```text
原问题
  → 解析全部显式型号
  → N1 授权检索 ─┐
                   ├→ 按实体交错合并 → 去重 → 证据校验 → 回答
  → MX550 授权检索 ┘
```

- 多实体产品咨询自动进入产品发现路径，不再错误收敛为一个型号。
- 每个型号独立调用 Knowledge Gateway，继承相同的租户、应用、环境和 Dataset 授权。
- 合并阶段按实体交错取证，避免一个实体填满全部证据预算。
- 并发 Gateway 请求使用随机 128-bit Trace ID；新增 1000 并发 ID 唯一性回归测试。
- Agent 单测断言发生两次检索，且最终引用同时包含 N1 与 MX550 文档。

## 真实验证

修复后同一问题返回 11 条合并证据，至少包含：

- `mindray-benevision-n1-2026`
- `philips-intellivue-mx500-mx550-2026`
- `sales-product-catalog-2026`

两个子检索拥有不同 Trace ID。独立 `agent-evaluation` 平台在同一冻结数据集上记录了前后运行：证据覆盖率和总通过率均从 87.5% 提升到 100%，质量门禁由失败变为通过。

最终联合验收运行 `pilot_78247cb6fc034a50bba0bb398d33a491` 再次执行全部 8 条冻结生产形态样本：通过率、决策准确率、引用合规、证据覆盖、数据集边界和安全指标均为 1.0，失败用例为 0，且没有写入生产配置。

## 经验

1. 答案正确不等于证据链完整，尤其是比较、组合和多跳问题。
2. Top-K 是全局预算时，需要先按实体或子问题分配候选配额。
3. 评测数据必须描述“应引用哪些资料”，不能只有预期答案关键词。
4. 并发检索不仅影响延迟，也会暴露 Trace ID、超时和结果合并等工程问题。
5. 这次延迟下降只是一轮网络样本，不能作为性能因果结论；性能结论需要多轮分位数统计。
